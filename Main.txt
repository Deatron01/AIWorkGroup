Executive SummaryThis document outlines the architecture for a fully local, offline-capable multi-agent AI software foundry. The system utilizes an event-driven microservice architecture to orchestrate a team of specialized AI agents (Boss, Supervisor, and Workers) operating within a secure, containerized workspace. To support hardware profiles ranging from 8GB to 24GB VRAM, the design heavily leverages quantized local models via a centralized inference server, decoupling the logical agent roles from the physical model weights to maximize throughput and prevent Out-Of-Memory (OOM) failures.1. System ArchitectureThe architecture is built on an asynchronous, event-driven backend utilizing Python and Docker. It avoids monolithic execution loops in favor of a message-passing design, allowing agents to operate, block, and complete asynchronously.Core ComponentsInference Engine (LLM Backend): A highly optimized local server (e.g., llama.cpp server or vLLM) that handles concurrent requests. Instead of loading separate models into VRAM for each agent, the engine loads 1-2 capable models and multiplexes agent requests using different system prompts and tool schemas.Orchestration Bus: An event bus (e.g., Redis or zeroMQ) that handles message routing between agents. State transitions (e.g., Task_Created, Code_Written, Verification_Failed) drive the system.Workspace Sandbox (Docker): A mounted volume that the agents can read/write to. Code execution and testing strictly occur inside an ephemeral Docker container to prevent accidental system damage.Context & Memory Store: A local vector database (ChromaDB or LanceDB) combined with SQLite for tracking project state, file trees, and conversational history without blowing up the LLM context window.UI & API Gateway: A FastAPI backend serving a desktop application (Tauri + React/Vue) to provide real-time observability.2. Agent Roles and CooperationThe agents operate in a strict hierarchy using a Directed Acyclic Graph (DAG) for task dependency management.The Boss (Planner)Responsibility: Goal decomposition and state management.Behavior: Receives the user prompt, reads the workspace file tree, and generates a JSON-formatted DAG of tasks. It does not write code. It routes tasks to specialized workers via the event bus and listens for Task_Completed or Task_Failed events to unblock dependent nodes.Tools: read_file_tree, create_task_graph, assign_worker, update_plan.The Supervisor (Verifier)Responsibility: Quality assurance and cyclic enforcement.Behavior: Acts as a gatekeeper. When a Worker finishes a task, the Supervisor intercepts it. It reads the code/diff, runs syntax checkers (e.g., pylint, clang-tidy), and executes the associated test suite within the Docker sandbox.Decision Matrix: If tests pass and code aligns with the Boss's spec, it emits Verification_Passed. If it fails, it emits Verification_Failed with a detailed critique, bouncing the task back to the Worker. Max retry loops are enforced (e.g., 3 retries) before escalating to the user.Tools: execute_bash_sandboxed, run_linter, run_tests, git_diff.The Workers (Specialists)Responsibility: Execution of concrete tasks.Specializations:Programmer: Writes and edits source code using AST-aware edit tools (not just blind regex).Tester: Writes unit and integration tests based on the spec before or alongside the Programmer (TDD approach).Architect: Generates PlantUML or Mermaid diagrams and architectural markdown.Tools: read_file, write_file_chunk, search_codebase (via local AST/grep).3. The models do not execute "parallel neural networks"; instead, the event loop runs in parallel. Multiple agents send prompts to the single API endpoint simultaneously. The server batches these requests at the token generation level, simulating a team of AI workers while adhering to strict VRAM constraints.4. UI, Logs, and Supervision LayerThe UI (Tauri + React) provides a "Control Room" for the software foundry.Task DAG Visualizer: A nodal graph (using React Flow) showing the Boss's plan. Nodes turn green (verified), blue (in progress), or red (failed).Agent Swimlanes: A live terminal feed split by agent. You can see the Worker generating code while the Supervisor executes bash commands.File Diff Review: A split-pane Monaco Editor showing what the Worker intends to change.Human-in-the-Loop (HitL) Gates: Configurable toggles allowing the user to pause execution before the Supervisor merges file changes to disk.Audit Log: Every LLM prompt, response, tool call, and terminal output is logged to a local SQLite database for traceability.5. Give it a hardcoded task, have the Worker write a file, and the Supervisor run a python script to check it.Phase 2: Orchestration & Docker SandboxIntroduce the Boss agent to parse a prompt into a JSON task array.Mount the target workspace to a Docker container.Implement execute_bash tool for the Supervisor, routing commands exclusively into the container.Phase 3: Event Bus & ParallelismMigrate from a linear script to an event-driven architecture (Redis/FastAPI).Allow two Workers to pick up non-dependent tasks simultaneously from the queue.Phase 4: UI & ObservabilityBuild the Tauri/React frontend.Stream SQLite logs to the UI via WebSockets for live updates.6. Test and Verification PlanFramework Unit Tests: The event bus, tool schemas, and file-editing logic must have strictly deterministic unit tests (using pytest).Mock LLM Testing: Create a dummy LLM class that returns pre-determined JSON strings to test the Supervisor's reaction to "bad code" without waiting for real inference.End-to-End Sandbox Test: Trigger the system to write a basic FizzBuzz program, write a unit test, and verify it automatically in Docker. This serves as the system health check.7.
